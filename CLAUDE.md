## What This Is

Poseidon Academy is a **mobile-first learning app for independent artists** — the music
business, explained in short lessons, plus a glossary and interactive tools. It works
fully offline with no backend.

It is a **separate app and a separate git repo** from the main Poseidon Music Platform
website. They share a design language (gold-on-black) and a parent topic (helping
independent artists), but no code, no database, and no server.

```bash
npm run build

npx cap add android      # one-time, requires Android Studio (generates android/ — gitignored)
npm run cap:ios          # build + cap sync ios + cap open ios
npm run cap:android      # build + cap sync android + cap open android
npm run cap:sync         # build + cap sync (both platforms)

`capacitor.config.ts` sets app id `com.poseidonholdings.academy`, app name
"Poseidon Academy", `webDir: 'dist'`, and dark `#0a0a0a` background.

The `ios/` and `android/` folders are **gitignored** until someone intentionally commits
them — they're regenerated by `cap add`.

## Architecture

No router. Navigation is a tiny custom store. This keeps the native bundle small and the
back behavior obvious.

### Navigation model (`src/context/NavContext.tsx`)

State is two things:
- `tab` — which of the 5 bottom tabs is active (`home | learn | tools | search | saved`).
- `detail` — an optional view stacked on top of the active tab, either
  `{ kind: 'lesson', id }` or `{ kind: 'category', id }`, or `null`.

Behavior:
- `setTab(tab)` switches tab and clears any open detail.
- `openLesson(id)` / `openCategory(id)` push a detail view.
- `back()` clears the detail view (returns to the tab).
- Switching tabs always drops the detail view (Instagram-style — each tab is "fresh").

`App.tsx` renders: if `detail` is set, show `LessonDetail` or `CategoryDetail`; otherwise
show the active tab's screen. `BottomNav` is always mounted underneath. Framer Motion's
`AnimatePresence` animates transitions.

**Note:** The `Tools` tab manages its own internal sub-view state (hub → Glossary or
ReleaseChecklist) with local `useState`, *not* through NavContext. That was a deliberate
simplification because the tools aren't lessons/categories. If you add more standalone
tools, consider promoting them into NavContext as a third `detail.kind`.

### Saved / bookmarks (`src/context/SavedContext.tsx`)

An array of bookmarked lesson IDs, persisted to `localStorage` under key
`poseidon.saved.v1`. `toggle(id)`, `isSaved(id)`, and `saved` (most-recent-first order).
Used by `LessonCard`, `LessonDetail`, and the `Saved` screen.

### Content model (`src/data/content.ts`) — the most important file

This is the single source of all content and the contract the UI renders against.

```ts
type Block =
  | { type: 'paragraph'; text: string }
  | { type: 'heading'; text: string }
  | { type: 'list'; items: string[] }
  | { type: 'callout'; text: string }
  | { type: 'steps'; items: string[] }

interface Lesson {
  id: string                 // unique slug, used in navigation + bookmarks
  categoryId: string         // must match a Category.id
  title: string
  summary: string            // one-line, shown on cards
  readMins: number
  level: 'Beginner' | 'Intermediate' | 'Advanced'
  body: Block[]              // structured — no raw HTML, nothing to sanitize
}

interface Category {
  id: string
  name: string
  blurb: string
  icon: string               // a lucide icon NAME — must be registered in Icon.tsx
}

interface GlossaryTerm {
  term: string
  definition: string
  category: string           // free-text grouping label (e.g. "Royalties")
}
```

Exports: `categories` (6), `lessons` (12), `glossary` (22). **All placeholder** — modeled
on real music-business topics but written to be replaced by the team's curated material.

### How to add / replace content (do this when the team delivers material)

1. **Lessons:** add objects to the `lessons` array. Give each a unique `id`, point
   `categoryId` at an existing category, and write the body as `Block`s. That's it — it
   appears in Learn, category pages, search, and is bookmarkable automatically.
2. **Categories:** add to `categories`. The `icon` must be a lucide icon **name** that is
   also added to the registry in `src/components/Icon.tsx` (see next point).
3. **Icons:** `Icon.tsx` is an explicit map, NOT a barrel import. Reason: `import * as
   Lucide` pulled ~700 kB of unused icons into the bundle. To use a new category icon,
   import it by name and add it to the `ICONS` record. Unknown names fall back to `Circle`.
4. **Glossary:** add to the `glossary` array. Powers both the Glossary tool and global Search.
5. **Featured lesson on Home:** `Home.tsx` has `FEATURED_ID = 'release-timeline'`. Update
   it if you rename/remove that lesson.
6. **Release Checklist:** its items are a separate hardcoded list inside
   `src/screens/tools/ReleaseChecklist.tsx` (`SECTIONS`), not in `content.ts`. Edit there.

| Token | Value | Use |

| `--color-bg` | `#0a0a0a` | page background |
| `--color-surface` | `#111111` | cards |
| `--color-surface-2` | `#161616` | pressed/active |
| `--color-border` | `#222222` | borders, dividers |
| `--color-muted` | `#888888` | secondary text |
| `--color-text` | `#ededed` | primary text |
| `--color-gold` | `#c9a94e` | accent (active tab, highlights, CTAs) |
| `--color-gold-soft` | `#e6cd86` | callout text |
| `--color-gold-dim` | `rgba(201,169,78,0.12)` | accent backgrounds |

Use Tailwind classes like `bg-surface`, `text-gold`, `border-border`. Safe-area helpers
`pt-safe` / `pb-safe` handle the iOS notch and home indicator. `index.html` sets
`viewport-fit=cover` and the dark theme-color so the native status bar matches.

## Conventions

- **No emojis in UI** — use Lucide icons (matches the website).
- **Icons are an explicit registry**, never `import * as Lucide` (bundle size).
- **`@/` is the alias for `src/`** — import as `@/components/...`, `@/data/content`, etc.
- **Content is structured, never raw HTML** — extend the `Block` union if you need a new
  layout, and handle it in `Blocks.tsx`.
- **No backend / network** — keep it that way for V1. If content needs to update without an
  app-store release later, that's a deliberate future decision (see Next steps).
- **Commit only when the user explicitly says to commit** (standing rule from the website
  project — applies here too).
- Build locally (`npm run build`) before any push to catch TypeScript errors early.
- Keep components small and match the existing Tailwind idiom (rounded-2xl cards,
  `border-border bg-surface`, `active:bg-surface-2` press states).
